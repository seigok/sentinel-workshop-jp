# Sentinel 提案ストーリー（お客様向け）

この章は、技術学習だけでなく、HashiCorp からお客様へ Sentinel を提案する際に使える「説明の型」をまとめたものです。

## 1. まず伝える価値

Sentinel の価値は、単なる「ルールを増やせる仕組み」ではありません。ポイントは以下です。

- **ガバナンスの標準化**: チームごとの暗黙知を、再利用可能なポリシーとして明文化できる
- **レビューの高速化**: 手作業チェックを減らし、例外の有無を機械的に判定できる
- **監査対応の強化**: 「誰が何を基準に許可/拒否したか」を説明しやすい
- **段階的導入が可能**: advisory → soft-mandatory → hard-mandatory の順で安全に運用成熟度を上げられる

## 2. 典型的な課題と訴求ポイント

### 課題 A: プロジェクトごとにルールがバラバラ
- 訴求: Policy Set で共通ガードレールを定義し、適用対象を柔軟に管理可能

### 課題 B: セキュリティレビューが属人化
- 訴求: CI / HCP Terraform 実行時に自動判定し、再現性のある審査へ移行

### 課題 C: 新規プロジェクトの立ち上げが遅い
- 訴求: テンプレート化されたポリシーセットを適用して初日から最低限の統制を実現

## 3. 提案時のデモ構成（30 分）

1. **現状の課題確認（5 分）**
   - 手作業レビューや例外対応の負荷を確認
2. **Sentinel の最小デモ（10 分）**
   - `true` / `false` の単純ポリシーとテストを実演
3. **実務ポリシーのデモ（10 分）**
   - 例: 危険な設定（広すぎる CIDR、タグ未設定など）を reject
4. **導入ロードマップ（5 分）**
   - advisory 運用から本番適用までの段階計画を提示

## 4. 導入ロードマップの例

- **Phase 1（可視化）**: advisory で現行運用に影響を与えず課題を把握
- **Phase 2（統制）**: 一部ポリシーを soft-mandatory 化し、例外承認フローを整備
- **Phase 3（定着）**: 重要ポリシーを hard-mandatory 化し、CI と監査証跡を運用へ統合

## 5. 成果指標（KPI）の例

- 変更レビューの平均所要時間
- 例外申請件数と承認リードタイム
- ポリシー違反の再発率
- 本番適用前に検知できた不備件数

## 6. 参考: よくある反論への返し方

- **「厳しくしすぎると開発が遅くなる」**
  - まず advisory で計測し、影響を見ながら段階適用する
- **「運用チームだけが得をして現場がつらい」**
  - 開発チームの手戻り削減（早期検知）を定量で示す
- **「ポリシー管理が増えて大変」**
  - 命名規則・ディレクトリ設計・CI により保守性を担保する

ワークショップ参加後は、本章を使って「技術デモ」と「導入提案」の両輪で説明できる状態を目指してください。
